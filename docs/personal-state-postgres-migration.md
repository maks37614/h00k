# h00k.top — перевірка перенесення персональних станів до PostgreSQL

## Поточний стан

**JSON залишається основним сховищем.** Файли `surveillance.json`,
`alerts.json` та `alert_history.json` можна *явно* скопіювати в
існуючий PostgreSQL, але це лише підготовча копія, не перемикання
працюючих 24/7-працівників, Telegram або API на SQL.

Telegram-прив'язки, черга Telegram, видалені алерти та інші JSON-файли
**не входять до цієї міграції**. Їх не можна оголошувати перенесеними
лише тому, що три таблиці перевірено.

## Перед перенесенням

1. Перевірити актуальну версію `main`, успішні тести, стан сервісів.
2. Запланувати коротке технічне вікно та призупинити нові зміни
   алертів, нагляду й історії. Три JSON-файли не можна отримати як
   єдиний узгоджений знімок, поки сервер їх змінює.
3. Зробити окремі резервні копії **обох** Docker-томів:
   `h00k_app_data` та PostgreSQL `h00k_pg_data`.
   Перевірити можливість відновлення і зберегти зашифровану копію
   поза VPS. **Не виконувати** `docker compose down -v`,
   `git reset --hard` чи видалення файлів/томів.
4. Перевірити доступні місце на диску та права доступу до резервних копій.
   Скрипт міграції не видаляє жодних користувацьких даних.

Приклад PostgreSQL backup із каталогу `/home/ubuntu/h00k`
(виконує оператор, не GitHub Actions):

```bash
cd /home/ubuntu/h00k
mkdir -p backups
chmod 700 backups
umask 077
docker compose exec -T postgres pg_dump -U h00k -Fc h00k_users \
  > "backups/h00k-users-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

JSON зберігається в Docker-томі `h00k_app_data`, а не обов'язково
в `/home/ubuntu/h00k/server/data`. Резервне копіювання цього тому
потрібно виконати окремо, з перевіркою, що архів містить усі файли.

## Підготовча копія

Команди виконуються лише після backup і узгодженого технічного вікна:

```bash
docker compose exec -T app node --import tsx server/pgStateMigrator.ts --dry-run
docker compose exec -T app node --import tsx server/pgStateMigrator.ts --apply
docker compose exec -T app node --import tsx server/pgStateMigrator.ts --verify
```

- `--dry-run`: підрахунок валідних рядків та SHA-256 джерела, без
  зміни трьох таблиць персональних станів.
- `--apply`: транзакційне **перше** копіювання до PostgreSQL.
  При конфлікті з уже зміненими рядками або іншим знімком джерела
  транзакція **повністю відкочується**. Якщо контрольна сума вже успішно
  перенесеного знімка збігається, повторна команда **нічого не копіює**
  (`alreadyStaged: true`, `verificationRequired: true`), щоб не
  відновити видалені користувачем алерти або записи історії.
  Після повторного `--apply` обов'язково запустіть `--verify`:
  успішний no-op не означає відсутність розбіжностей.
  Не обходьте захист видаленням staging-маркерів чи перезаписом таблиць.
- `--verify`: **повністю read-only перевірка PostgreSQL**, без
  створення таблиць, запису чи зміни JSON. Читає стабільний SQL-знімок
  і порівнює вміст та індексовані поля всіх трьох таблиць.
  Виводить тільки загальні лічильники: `matched`, `missing`,
  `different`, `extra`, і відповідність SHA-256 маркера.

`consistent: true` і код виходу 0 означає, що ці три підготовчі таблиці
збігаються з поточним прочитаним JSON-знімком. Код виходу 2 означає
розбіжності; код 1 — помилку читання/SQL. **Це не гарантує,
що за час перевірки живий сервер не змінив JSON**, тому для
майбутнього реального перемикання потрібна контрольована пауза записів.

Не записуйте у логи вміст `.env`, приватні Telegram chat ID, дані
особистих сповіщень або паролі PostgreSQL. Скрипт повідомляє лише
агреговані значення й контрольну суму.

## Правило перемикання

**Не перемикати runtime на PostgreSQL лише за результатом цього скрипта.**

Окремий етап повинен атомарно зберігати всі майбутні зміни в SQL,
враховувати видалення, синхронізувати Telegram-доставку та
ідемпотентні ключі, відновлювати 24/7-працівників після рестарту,
і мати зворотній план без повторного відправлення сигналів.
До впровадження та перевірки цих механізмів JSON лишається
єдиним джерелом істини для відповідних функцій.

Жодних тестів фактичного навантаження VPS ці команди не запускають.
